# Database benchmarks

What this measures: the same application queries on the **original** (pre-cleanup) schema and on the schema produced by
the `20261015_*` cleanup migrations, on a real PostgreSQL 17 server with about one million certificates. It is a
database benchmark, not an end-to-end HTTP load test: it does not include Supabase's API layer, the network or the
Next.js server.

## Setup

| | |
|---|---|
| Server | PostgreSQL 17.11 in Docker Desktop (WSL2), 4 vCPU, about 6 GB RAM, `shared_buffers=1GB` |
| Host | Intel i5-13450HX, Windows 11 |
| Schema "before" | `supabase/tests/live-schema.sql`, the model of the production schema (17 tables, 109 indexes, matches the live introspection) |
| Schema "after" | the same database after migrations `20261015_00` to `08` plus `03b`, applied to a copy of the loaded data |
| Data (synthetic, generated by `scripts/bench-db/seed.sql`) | 1,000,006 certificates, 1,000,003 audit rows, 280,005 credentials, 102,007 users and profiles, 43 organizations |
| Load | `pgbench`, 8 concurrent clients, 5 s warm-up then 20 s measured per query, one run per query; latency percentiles from the per-transaction log |
| Queries | the shape of the application's real queries (`scripts/bench-db/q/*.sql`) |

## Results (milliseconds, 8 concurrent clients)

| Query | p50 before | p50 after | p95 before | p95 after | throughput before | throughput after |
|---|---:|---:|---:|---:|---:|---:|
| Credential lookup by certificate | 433.8 | **0.102** | 1,012.8 | **0.185** | 15 / s | **70,420 / s** |
| Insert a certificate | 5.29 | **1.06** | 11.30 | **1.55** | 1,323 / s | **6,967 / s** |
| Faculty review queue (pending, one organization) | 1.06 | **0.245** | 1.94 | **0.49** | 7,118 / s | **29,134 / s** |
| A student's certificates | 0.237 | **0.146** | 0.453 | **0.248** | 31,500 / s | **51,168 / s** |
| Role lookup (every authenticated request) | 0.132 | 0.115 | 0.215 | 0.196 | 57,033 / s | 64,472 / s |
| Audit log, latest 50 for an organization | 0.195 | 0.176 | 0.340 | 0.321 | 38,640 / s | 41,478 / s |
| Organization analytics (count by status, about 25k rows) | 46.2 | 49.1 | 56.0 | 62.6 | 170 / s | 156 / s |

Reading the table honestly:

- **Credential lookup:** the old code found a credential by JSON containment on the signed credential (no usable index),
  so every call was a parallel sequential scan of 280,000 rows (35,000 buffers, 103 ms for a single unloaded
  execution). The new `certificate_id` column with an index answers in 0.035 ms for a single execution (4 buffers). With 8
  clients competing, the median call went from 434 ms to 0.1 ms.
- **Insert:** certificates carried 21 indexes before and carry 5 now, so each insert writes less.
- **Review queue:** the old index could not use the status filter, so one execution read 1,035 buffers and discarded 976
  rows to return 50; the new composite `(organization_id, verification_status, created_at)` index reads 53 buffers.
- **Role, audit and analytics queries are essentially unchanged** (10 to 13 percent better at the median, which is within the
  run-to-run noise of a single 20 s run, so do not quote it as an improvement). The organization analytics query is slightly slower, not faster: it is
  scan-bound and was not what the cleanup targeted. A materialised aggregate would be the fix.

## Size and shape

| | before | after |
|---|---:|---:|
| Tables | 17 | 13 |
| Indexes | 109 | 54 |
| Indexes on `certificates` | 21 | 5 |
| `certificates` index size | 309 MB | 166 MB |
| `audit_logs` index size | 290 MB | 195 MB |
| `verifiable_credentials` index size | 23 MB | 57 MB (new lookup indexes) |
| Whole database | 1,587 MB | 1,997 MB |

The whole database is larger after the migration, not smaller: the migration adds columns (some backfilled on every
row) and rewrites tables, and the space of the old row versions is not returned without a `VACUUM FULL`. Only the
index footprint shrank.

## Migration at scale

The nine migration steps (plus `03b`) were applied to a copy of the loaded database with timings in
`benchmarks/migration-timings.txt`:

| Step | Time |
|---|---:|
| 00 preflight | 3.7 s |
| 01 expand (new columns, backfills across 1M rows) | 213.6 s |
| 02 integrity (constraints, triggers, type changes) | 22.7 s |
| 03 indexes | 5.7 s |
| 03b, 04, 05, 06, 07, 08 | under 0.7 s each |
| **Whole chain** | **about 4 minutes** |

Step 01 is the only long one; it is additive and the application keeps working while it runs.

## Limits of these numbers

- The data is synthetic and uniformly distributed; real data is skewed.
- One run of 20 s per query on one machine, no repeats: treat differences under about 15 percent as noise.
- The caches are warm (the data set fits in memory); a cold cache would widen the gap for the old plans, since they read
  far more pages.
- The "before" schema is a model of production (matching table and index counts), not a dump of the live database.
- Latency here is database time only. A request through the HTTP API adds network and application time that this
  benchmark does not measure.

## Reproduce

Needs Docker (about 6 to 8 GB of Docker disk at the peak, 15 to 20 minutes):

```
bash my-app/scripts/bench-db/orchestrate.sh     # results land in ./bench-out
docker rm -f -v cs-bench                         # clean up
```

The raw numbers from the run above are in `docs/benchmarks/`.

## Other measured numbers (in-process, no database)

`node scripts/bench-verify.mjs`, `bench-merkle.mjs` and `bench-sdjwt.mjs` print their own results (single thread,
warm): offline credential verification about 6,000 per second (p50 0.146 ms), a Merkle inclusion proof over 100,000
entries p50 3.8 microseconds, selective-disclosure issue and verify p50 0.41 ms and 0.24 ms. These modules are optional
and off in the hosted deployment.
